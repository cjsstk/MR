# 1. 이동 버벅임 — 정상 이동이 어뷰징으로 오탐되던 버그 ⭐
`QSEV-43383`, `QSEV-45786`

**상황(S)**: 특정 구간(노래의 땅)이나 탈것 자동이동 중 캐릭터가 순간 멈췄다 튕기는 버벅임 발생.

**문제(T)**: 서버의 이동 어뷰징(스피드핵) 검사가 원인. 클라이언트 히칭이나 존 전환 직후 밀렸던 이동 요청이 몰려 들어오면 `reqDeltaSeconds`가 커져 **미래 시간(future delta) 어뷰징으로 오판정** → 서버가 위치 보정을 반복하는 루프에 빠짐. 시간차 허용 오차가 0으로 설정된 게 근본 원인.

**해결(A)**: 검증식에 허용치 `_abuseMaxDeltaSeconds(0.34s)`를 더해, 클라 히칭 수준의 시간차는 정상 통과시키되 실제 어뷰징은 여전히 걸러지도록 임계값을 조정.
```
// before
if (reqDeltaSeconds > preDeltaSeconds * _abuseMinErrorSeconds)
// after
if (reqDeltaSeconds > preDeltaSeconds * _abuseMinErrorSeconds + _abuseMaxDeltaSeconds)
```

**배운점(R)**: 증상(클라 버벅임)과 원인(서버 검증 로직)이 다른 계층에 있어 추적이 까다로웠음. 보안 검사를 무력화하지 않으면서 정상 케이스만 통과시키는 균형이 핵심.

### 예상 꼬리질문 & 모범답안
- **Q. 원인을 어떻게 특정했나요?**
  A. 버벅임이 발생하는 위치·상황(존 전환 직후, 자동이동)에 공통점이 있었고, 서버 어뷰징 로그(`mov ftr delta`)가 그 타이밍에 찍히는 걸 확인해 보정 루프를 의심했습니다. 클라 이슈로 보이지만 실제로는 서버 판정이 원인이었습니다.
- **Q. 0.34초라는 값은 어떻게 정했나요?**
  A. 실제 클라 히칭·RTT 편차 범위를 로그로 관찰해 정상 편차는 흡수하면서 비정상 가속은 못 넘도록 정한 경험적 임계값입니다. 상수로 빼서 튜닝 가능하게 했습니다.
- **Q. 이러면 어뷰징에 취약해지지 않나요?**
  A. 허용치는 '한 틱 분량의 시간차'수준으로 작아, 지속적인 속도 이득은 누적 검사에서 여전히 걸립니다. 순간적인 한 번의 편차만 눈감아주는 트레이드오프입니다.
- **Q. 더 근본적인 해결책은?**
  A. 서버 권위(server-authoritative) 이동에서 클라 타임스탬프를 신뢰 구간으로 보정하거나, 요청을 큐잉해 틱 단위로 정규화하는 방법이 있습니다. 다만 라이브 안정성과 비용을 고려해 최소 변경으로 대응했습니다.

# 2. 보스 다단 스킬 콤보 시스템 설계 ⭐
`QSEV-51001` (+ `UseActiveComboSkill`, `Interval` 개선)

**상황(S)**: 기존 AI 비헤이비어 트리의 Combo 노드는 한 페이즈에 스킬을 **하나만** 사용 가능. 기획에서 한 페이즈에 여러 스킬을 연계 요청.

**해결(A)**: `SkillCombo` 노드를 신규 설계 — 자식 스킬 노드들을 읽어 하나씩 예약하고 각 스킬이 끝날 때까지 대기. 도입 후 파생된 문제들을 반복 개선:
- **글로벌 쿨타임 충돌** → 스킬 사이 딜레이용 `ComboDelay` 노드 추가 → 이후 글로벌 쿨타임을 자동 체크하도록 개선해 딜레이 노드 없이도 연속 시전 가능.
- **타겟 이탈 시 콤보 끊김** → 타겟이 죽으면 재탐색 후 예약하는 `UseActiveComboSkill` 노드 추가.
- **Interval 노드 시간 누적 멈춤** → SkillCombo가 Running으로 유지되는 동안 Interval 시간이 안 흐르던 문제를, 누적 방식이 아닌 시작–현재 시각 비교 방식으로 변경.

**배운점(R)**: 새 시스템 도입 후 파생되는 엣지 케이스를 스스로 발견하고 반복 개선하는 과정이 중요했음.

### 예상 꼬리질문 & 모범답안
- **Q. 왜 상태머신이 아니라 비헤이비어 트리 노드로 확장했나요?**
  A. 기존 몬스터 AI가 비헤이비어 트리 기반이라 기획자가 노드를 조합해 패턴을 구성하는 워크플로가 이미 있었습니다. 새 노드로 추가하면 기존 도구·데이터 흐름을 그대로 활용하고 재사용성이 높아집니다.
- **Q. '예약(reserve) 후 대기' 구조로 만든 이유는?**
  A. 스킬 시전에는 선딜/후딜·애니메이션 종료 시점이 있어, 즉시 다음 스킬을 굴리면 글로벌 쿨타임에 막혀 실패합니다. 각 스킬의 종료를 기다렸다 다음을 예약해야 연계가 안정적으로 동작합니다.
- **Q. Interval 누적 방식을 왜 시각 비교로 바꿨나요?**
  A. 누적 방식은 노드가 매 틱 실행돼 시간을 더해야 하는데, SkillCombo가 Running으로 트리를 잡고 있으면 Interval이 호출되지 않아 시간이 멈춥니다. 시작 시각과 현재 시각을 비교하면 그 사이 호출이 없어도 콤보 종료 직후 경과 시간을 정확히 반영할 수 있습니다.
- **Q. 콤보 도중 페이즈 전환이 겹치면?**
  A. 콤보는 완결 단위로 처리하고, 우선순위 높은 페이즈/체력 트리거는 상위 노드에서 인터럽트하도록 설계 방향을 잡을 수 있습니다. (실제 요구에 맞춰 확장)

# 3. 명중률 스킬의 '빗나감' 오노출 — 서버 부수효과까지 고려 ⭐
`QSEV-51790`

**상황(S)**: 확률(Hitper) 기반 데미지 스킬이 안 터졌을 때 "빗나감" 플로터가 뜨고, 회피 시 발동하는 **프록(proc) 등 부가 효과까지 트리거**됨.

**핵심 판단**: 클라에서 플로터만 숨길 수도 있었지만, 회피 판정에 딸린 서버 부수 효과 때문에 **서버에서 아예 다른 판정 경로**로 처리하기로 결정.

**해결(A)**: 회피 판정 *이전에* 확률을 굴려, 실패 시 `SkillChanceFail` 태그로 분기 → 이펙트/플로터/프록 모두 발동 안 되게 처리.
```cpp
int64_t const rnd = CL::RandRangeInc(1000LL, 1LL);
if (rnd > damageRow->Chance) {
    inOutResult._tags.SetOn(EApplyTag::SkillChanceFail);
    return 0LL;               // 아무 효과 없이 종료
}
hitper = 1000LL;             // 확률은 위에서 이미 판정 → 회피 판정은 통과시킴
```
그리고 결과 적용 단계에서 `SkillChanceFail` 태그가 있으면 continue로 건너뜀.

**배운점(R)**: "화면만 가리는 임시방편"이 왜 위험한지 — 회피라는 상태에 다른 시스템(프록)이 물려 있었음. 근본 원인이 있는 계층에서 고쳐야 함.

### 예상 꼬리질문 & 모범답안
- **Q. 왜 클라에서 플로터만 숨기면 안 됐나요?**
  A. '빗나감=회피'로 처리되면 회피에 반응하는 서버 로직(프록, 반격 등)이 함께 발동합니다. 클라만 가리면 화면은 깨끗해도 서버 상태는 여전히 잘못되므로, 판정 자체를 분리해야 했습니다.
- **Q. 확률 판정을 회피 판정 앞으로 옮긴 이유는?**
  A. 순서가 핵심입니다. 회피보다 먼저 굴려 실패면 '아무 일도 없었던 것'으로 조기 반환하고, 성공하면 회피 로직에는 영향을 안 주려고 hitper를 최대치로 넘겨 통과시켰습니다.
- **Q. 난수 재현성/검증은?**
  A. 서버 권위 난수를 사용하므로 클라와 불일치가 없고, 태그 기반 분기라 로그로 결과를 추적·검증할 수 있습니다.

# 4. 군중제어(CC) 면역 시스템 — 데이터 주도 설계
`QSEV-51285`

**상황/해결(A)**: 특정 상태이상에 걸리면 지정한 CC들에 면역되도록 `ImmuneCrowdControlGroup` 테이블과 `StatusChangeEffect` 컬럼을 추가한 **데이터 주도(data-driven) 설계**. 기획자가 코드 수정 없이 CSV로 면역 조합을 구성. 추가로 모든 CC가 면역이면 클라에서 불필요한 CC 이펙트를 출력하지 않도록 처리.

**배운점(R)**: 확장 가능한 테이블 기반 설계 + 클라 연출까지 챙긴 완결성.

### 예상 꼬리질문 & 모범답안
- **Q. 왜 하드코딩 대신 테이블로 뺐나요?**
  A. 면역 조합은 콘텐츠마다 자주 바뀝니다. 코드에 박으면 매번 빌드/배포가 필요하지만, 테이블로 빼면 기획자가 데이터만 수정해 즉시 반영·검증할 수 있어 개발 병목이 사라집니다.
- **Q. 그룹 테이블로 묶은 이유는?**
  A. 여러 CC를 하나의 '면역 그룹'으로 참조하면 재사용과 일괄 수정이 쉽습니다. SC마다 CC 목록을 나열하는 것보다 정규화된 구조라 데이터 중복이 줄어듭니다.
- **Q. 클라에서 이펙트를 왜 별도로 막았나요?**
  A. 서버가 CC를 면역 처리해도 클라는 연출을 미리/독립적으로 재생할 수 있어, 걸리지도 않은 CC 이펙트가 보일 수 있습니다. 모두 면역이면 연출을 생략해 오해를 없앴습니다.

# 5. 익명 던전 PvP 적대 관계 처리
`QSEV-50166`, `QSEV-50107`, `QSEV-49935` (권능의 신전 / 금기의 미궁)

**상황/해결(A)**: PvP 기본 관계가 Neutral인데, 익명 경쟁 던전에서는 우리 팀/길드만 빼고 적대 처리가 필요. 던전별로 PvP 관계를 Hostile로 설정하는 컬럼을 추가하고, 팀/길드 예외 처리 및 타팀 익명화·팀마크·번호 표시 로직을 구현.

**배운점(R)**: 콘텐츠 요구사항을 시스템 규칙(faction rule)으로 일반화한 경험.

### 예상 꼬리질문 & 모범답안
- **Q. 적대 판정을 어디서 하나요?**
  A. 유닛 간 관계(faction) 계산 지점에서 던전 규칙을 함께 평가합니다. 기본 관계 위에 던전 오버라이드(Hostile)를 얹고, 같은 팀/길드는 예외로 제외하는 우선순위 규칙입니다.
- **Q. 익명화는 왜 필요했나요?**
  A. 경쟁 던전에서 상대 신원이 노출되면 사적 감정/보복 문제가 생깁니다. 팀마크와 번호로 대체해 공정성과 몰입을 유지했습니다.

# 6. 채널링 '당기기(진공 흡입)' 기능 — 풀스택 + 1번과 연결 ⭐
`QSEV-47766` (+ `QSEV-49333`, `QSEV-49456`)

**상황(S)**: 보스가 채널링을 걸면 주변 유닛들이 타겟 쪽으로 서서히 빨려오는 기능 신규 구현. **서버·클라 양쪽** 작업.

**문제와 해결(A) — 여러 겹**:
- 서버: 0.1초 틱마다 유닛을 타겟 쪽으로 이동시키고 `FZ2CActorStartImpulse`/`EndImpulse` 패킷 전송.
- **어뷰징 시스템 충돌** → 서버가 강제로 위치를 옮기니 클라의 마지막 요청 위치와 어긋나 이동 어뷰징에 걸림. **매 틱 마지막 요청 위치를 현재 위치로 갱신**해 오탐 방지. (→ 1번 이슈와 같은 시스템)
- **로컬 유닛 버벅임** → 원격 유닛은 이동 보간 최적화가 있지만 로컬 유닛은 동기화 위치로 즉시 이동해 툭툭 끊김. Impulse 중에는 로컬 유닛도 **보간 이동**하도록 처리. 체력바도 동일 적용.
- **후속 버그**: 채널링이 적용하는 상태이상이 CC 면역 체크를 건너뛰고 무조건 적용되던 문제 수정, 보스는 당겨지지 않도록 제외.

**배운점(R)**: 서버 로직·네트워크 동기화·클라 보간·어뷰징·CC 면역까지 한 기능에 얽힌 여러 시스템을 통합적으로 다룬 경험.

### 예상 꼬리질문 & 모범답안
- **Q. 당기는 이동을 왜 서버에서 계산했나요?**
  A. 위치는 서버 권위여야 조작·불일치를 막을 수 있습니다. 서버가 매 틱 목표 위치를 계산해 Impulse로 내려주고, 클라는 그걸 부드럽게 표현만 합니다.
- **Q. 어뷰징 오탐은 어떻게 막았나요?**
  A. 강제 이동으로 클라의 마지막 요청 위치와 서버 위치가 벌어지면 어뷰징으로 잡힙니다. 그래서 Impulse가 적용되는 동안 서버가 기준이 되는 '마지막 요청 위치'를 현재 위치로 갱신해 정상 이동으로 인식되게 했습니다.
- **Q. 로컬 유닛만 버벅인 이유는?**
  A. 원격 유닛은 원래 지연 보상을 위해 보간 이동을 하지만, 로컬 유닛은 반응성을 위해 동기화 위치로 즉시 스냅합니다. Impulse 중에는 서버가 매 틱 위치를 바꾸니 그 스냅이 끊김으로 보여, 이때만 보간하도록 예외 처리했습니다.
- **Q. 왜 0.1초 틱인가요?**
  A. 너무 촘촘하면 패킷/연산 비용이 크고, 너무 성기면 이동이 계단처럼 보입니다. 보간과 결합해 자연스러움과 비용의 균형점으로 0.1초를 택했습니다.

# 9. 이펙트 최적화 옵션의 한계 파악과 우회
`QSEV-44917`

**상황(S)**: "상시 이펙트 최적화" 옵션을 켜면 칼레바르의 수레 안전범위 이펙트가 안 보임.

**핵심 분석**: 최적화는 **유닛 생성 시점에 이펙트 부착 여부를 결정**하는 방식이라 실시간 토글이 안 되는 구조적 한계가 있음을 파악.

**해결(A)**: 필수 연출인 수레 이펙트는 최적화 옵션의 영향을 받지 않도록 예외 플래그 처리.

**배운점(R)**: 성능 최적화 기능의 동작 원리와 트레이드오프를 이해하고, 무리하게 구조를 바꾸는 대신 실용적으로 예외 처리한 판단.

### 예상 꼬리질문 & 모범답안
- **Q. 왜 실시간 토글로 안 고쳤나요?**
  A. 실시간 부착/해제로 바꾸면 모든 이펙트 생명주기를 옵션 변화에 반응하도록 재설계해야 해 위험·비용이 큽니다. 문제는 '게임플레이에 필수인 이펙트가 최적화 대상에 포함된 것'이라, 그 이펙트를 최적화 예외로 두는 게 정확한 해법이었습니다.
- **Q. 최적화가 왜 생성 시점에만 동작하나요?**
  A. 매 프레임 판단하면 그 자체가 비용입니다. 스폰 시 한 번 결정하는 편이 저렴하고, 대부분의 이펙트는 생성 후 옵션이 바뀔 일이 드물어 합리적 설계입니다.

# 11. 상태이상 HUD 이펙트 복원 순서 버그
`QSEV-46923` (먹물 SC)

**상황(S)**: 먹물 상태이상이 지속 중 중복 적용되면 HUD 이펙트(화면 머터리얼)가 사라짐.

**원인/해결(A)**: 다른 애니메이션이 시작되면 기존 애니메이션의 Restore가 동작하지 않는 **머터리얼 복원 타이밍 충돌**. Restore를 별도로 정의하고, 데이터 테이블에 머터리얼이 있는 경우에만 세팅하도록 처리.

**배운점(R)**: 상태 중첩/복원 같은 엣지 케이스와 리소스 정리 순서 문제를 정확히 짚어낸 사례.

### 예상 꼬리질문 & 모범답안
- **Q. 왜 이펙트가 사라졌나요?**
  A. 중복 적용으로 새 애니메이션이 시작되면 이전 애니메이션의 종료 콜백(Restore)이 원래 머터리얼로 되돌려버려, 아직 유효한 효과의 화면 연출까지 지워졌습니다.
- **Q. 어떻게 고쳤나요?**
  A. Restore 로직을 애니메이션 흐름과 분리해 명시적으로 정의하고, 머터리얼이 지정된 경우에만 적용하도록 조건을 좁혀 유효한 상태의 연출이 유지되게 했습니다.
